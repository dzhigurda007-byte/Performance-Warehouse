# Архитектура и обоснование решений

Документ объясняет, **почему** приложение устроено именно так, со ссылками на практики
1С:Управление торговлей / 1С:WMS, специализированных WMS (адресное хранение) и МойСклад.

## 1. Учётная модель: справочники → документы → регистры

Как в 1С, данные разделены на три слоя:

| Слой | Таблицы | Аналог в 1С |
|---|---|---|
| Справочники | `users`, `warehouses`, `racks`, `cells`, `boxes`, `items` | Справочники «Склады», «Складские ячейки», «Упаковки», «Номенклатура» |
| Документы | `documents` + `doc_lines` | «Приходный ордер на товары», «Расходный ордер на товары», «Перемещение» |
| Регистры | `stock` (остатки), `moves` (движения) | Регистры накопления «Товары в ячейках», «Движения товаров» |

**Остатки никогда не правятся вручную.** Они меняются только проведением документа,
а каждое проведение пишет строки в `moves`. Поэтому история «кто, когда, что и откуда взял»
всегда сходится с остатками, а отмена проведения (как в 1С) возвращает остатки ровно на
сумму движений документа.

Проведение выполняется в одной транзакции: если хоть одной строки не хватает, не
применяется ничего (см. тест «проведение атомарно»).

## 2. Адресное хранение: Склад → Стеллаж → Ячейка → (Короб) → Товар

- **Ячейка** — минимальный адрес. Код формируется как в WMS: `ярус-место` (`1-01`, `4-10`),
  полный адрес — `СК1 / A / 1-03`. Ячейки создаются сеткой (ярусы × места).
- **Короб** — это «грузоместо» / LPN (License Plate Number) из WMS: у него свой
  QR-код `BX-000001`, он лежит в ячейке и может перемещаться.
- Остаток (`stock`) привязан **либо к ячейке, либо к коробу** (ровно одно поле, CHECK в БД).
  Ячейка короба берётся из `boxes.cell_id`. Отсюда два важных следствия:
  1. Перемещение короба — это изменение одного поля, содержимое «едет» вместе с ним
     (в журнал пишутся движения −/+ по каждому товару, чтобы история ячеек была верной).
  2. В одной ячейке одновременно может быть сколько угодно товаров россыпью и коробов.

## 3. Маркировка QR

Внутренние коды самоописывающие (как SSCC/LPN):

| Объект | Содержимое QR | Пример |
|---|---|---|
| Ячейка | `PW:C:<id>` | `PW:C:15` |
| Короб | `PW:B:<код>` | `PW:B:BX-000007` |
| Товар | `PW:I:<артикул>` | `PW:I:TM-00012` |

Любой другой код (EAN-13, Code128, DataMatrix производителя) ищется по полю «штрихкод»
товара, затем по артикулу и коду короба. Неизвестный штрихкод при приёмке предлагается
сразу завести новым товаром — так работает приёмка в МойСклад.

Этикетки печатаются через системную печать (AirPrint / Android Print) или сохраняются в PDF;
предусмотрена массовая печать всех ячеек стеллажа / склада.

Сканирование: камера телефона + поле ввода, которое принимает данные и от **аппаратного
сканера ТСД** в режиме эмуляции клавиатуры (Zebra, Urovo, Honeywell и т.п.).

## 4. Документы

### Приходный ордер (ПО)
Режим «ячейка приёмки» из WMS: оператор один раз сканирует/выбирает место (ячейку или
короб, можно создать новый короб прямо из диалога), затем сканирует товары — каждый
попадает в выбранное место. Повторный скан того же товара в то же место увеличивает
количество (свёртка строк, как в МойСклад). Место любой строки можно поменять до проведения.

### Расходный ордер по заявке (РО, режим `plan`)
Пользователь указывает **что** и **сколько** выдать, система сама подбирает **откуда**:
стратегия FIFO (сначала старые поступления), при равной дате — россыпь раньше коробов
(не вскрывать лишнее), затем места с меньшим остатком (освобождать ячейки).
Уже зарезервированное строками документа учитывается. Печатная форма отсортирована
по адресу и содержит колонку отметки — это одновременно **лист подбора** (pick list).
Любую строку можно перенаправить на другое место хранения.

### Расходный ордер по факту (РО, режим `fact`)
Для ситуации «человек подошёл и взял»:
- сканирует **QR короба** → видит содержимое → выбирает товар → количество;
  короб становится «открытым», и следующие товары в первую очередь берутся из него;
- сканирует **QR ячейки** → видит всё, что в ней (россыпь + содержимое коробов);
- сканирует **штрихкод/QR товара** без короба → если товар лежит в одном месте, оно
  подставляется само, если в нескольких — предлагается выбор (по FIFO);
- либо выбирает из общего списка остатков.

Количество ограничено доступным остатком с учётом строк документа. После ввода количества
сканер открывается снова — непрерывный режим, как на ТСД.

Для расхода обязательно поле **«Получатель»** — оно попадает в журнал движений.

### Перемещение короба (ПМ)
Сканировать короб → выбрать/отсканировать новую ячейку. Документ проводится сразу.

## 5. История ТМЦ
Вкладка «История» — журнал регистра `moves`: дата/время, товар, ±количество, адрес и короб,
кто оформил (пользователь), кому выдано (получатель), номер документа. Фильтры: выдача /
поступление, сотрудник, поиск по товару / получателю / номеру. История также есть в карточке
товара и короба.

## 6. Аккаунты
Регистрация: логин + ФИО + пароль, без e-mail и подтверждений. Пароль хранится как
соль + многократный SHA-256. Сессия сохраняется до выхода. Каждый документ хранит, кто его
создал и кто провёл.

## 7. Технологии

| Задача | Решение |
|---|---|
| Платформа | React Native + Expo SDK 57 (iOS / Android из одного кода), TypeScript |
| Навигация | Expo Router (файловая маршрутизация, `src/app`) |
| Хранение | SQLite (`expo-sqlite`), миграции через `PRAGMA user_version` |
| Сканирование | `expo-camera` (QR, EAN, Code128, DataMatrix …) |
| QR-генерация | `qrcode-generator` → SVG (`react-native-svg`) |
| Печать | `expo-print` (HTML → принтер / PDF) |
| Тесты | `node:test` + реальный SQLite (`node:sqlite`) через адаптер API expo-sqlite |

## 8. Ограничения MVP и дорожная карта

Сейчас база локальная (offline-first, на устройстве). Для работы нескольких сотрудников с
разных телефонов следующий шаг — **сервер синхронизации**:

1. Backend (NestJS/Go + PostgreSQL) с той же схемой; приложение остаётся offline-first,
   документы синхронизируются при появлении связи; проведение — на сервере
   (единый источник остатков, защита от двойного списания).
2. Роли: кладовщик / начальник склада / администратор (сейчас все пользователи равноправны).
3. Инвентаризация ячейки/короба по сканированию (документ «Пересчёт» с актом расхождений).
4. Подтверждение подбора сканированием (скан ячейки → скан товара по каждой строке).
5. Серии / партии / сроки годности (FEFO вместо FIFO), серийные номера.
6. Обмен с 1С (EnterpriseData / CommerceML) и МойСклад (JSON API 1.2): выгрузка номенклатуры
   и проведённых ордеров.
7. Печать на термопринтеры этикеток (Zebra ZPL / TSC TSPL) по Bluetooth.
